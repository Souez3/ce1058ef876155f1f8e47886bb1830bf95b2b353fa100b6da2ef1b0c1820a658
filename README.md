# Darkstore — сервис доставки продуктов

Серверная часть даркстора: каталог товаров, складские остатки с резервированием,
оформление и обработка заказов, авторизация с ролями персонала.
Реализовано как модульный монолит на Kotlin + Spring Boot, данные хранятся в PostgreSQL.

## Зачем это приложение

Сервис быстрой доставки продуктов для небольшого города (около 30 тысяч жителей),
где нет крупных федеральных сервисов доставки. Модель — даркстор: закрытый склад
без покупателей в зале, откуда заказы собираются и доставляются своими курьерами.

**Кому и зачем:**
- **Покупателям** — заказать продукты с телефона и получить их в течение дня,
  в том числе без регистрации, а постоянным клиентам — оплатить наличными при получении.
- **Сотрудникам склада** — видеть очередь заказов на сборку и актуальные остатки,
  не продавать товар, которого физически нет.
- **Курьерам** — видеть готовые к доставке заказы с адресом и телефоном клиента.
- **Менеджеру** — управлять ассортиментом и ценами, контролировать оплату и
  весь путь заказа от оформления до завершения.

**Масштаб на старте:** один склад, 2–3 курьера. Поэтому система построена как
модульный монолит: её просто развернуть и сопровождать, а модули при росте
можно выделить в отдельные сервисы.

## Возможности

**Каталог**
- Просмотр и поиск товаров без авторизации: по тексту, категории, подкатегории, диапазону цен, с пагинацией и сортировкой
- Дерево категорий и подкатегорий
- Создание, изменение и мягкое удаление товаров (менеджер, администратор)

**Склад**
- Остатки по каждому товару: общее количество, зарезервированное, доступное
- Приход товара с закупочной ценой (склад, менеджер, администратор)
- Резервирование при оформлении заказа, списание при сборке, снятие резерва при отмене
- Защита от одновременного резервирования одной позиции (оптимистичная блокировка, ответ 409)

**Заказы**
- Оформление заказа гостем или авторизованным клиентом
- Итоговая сумма считается на сервере по текущим ценам, цена фиксируется в позиции заказа
- Оплата наличными доступна только авторизованному клиенту и только на номер его аккаунта
- Заказ атомарен: если одной позиции не хватает на складе, не резервируется ничего
- Жизненный цикл: `CREATED → PAID → ASSEMBLED → SHIPPED → DELIVERED → COMPLETED`, а также `CANCELLED`
- Каждый переход проверяется по допустимому предыдущему статусу и по роли
- Изменение состава заказа персоналом до сборки (добавить, изменить количество, удалить позицию)
- Клиент видит свои заказы и может отменить свой заказ

**Пользователи и доступ**
- Регистрация и вход по номеру телефона (номер нормализуется: `8 (912) 345-67-89` → `+79123456789`)
- JWT access-токен (15 мин) и refresh-токен (30 дней) с ротацией: повторное использование старого refresh-токена отзывает все токены пользователя
- Роли: `CLIENT`, `MANAGER`, `WAREHOUSE_STAFF`, `COURIER`, `SYSTEM_ADMIN`
- Создание сотрудников администратором

| Действие | Роли |
|---|---|
| Каталог, оформление заказа | все, включая гостей |
| Свои заказы, отмена своего заказа | авторизованный пользователь |
| Управление товарами | MANAGER, SYSTEM_ADMIN |
| Склад, сборка заказа | WAREHOUSE_STAFF, MANAGER, SYSTEM_ADMIN |
| Отгрузка и доставка | COURIER, MANAGER, SYSTEM_ADMIN |
| Оплата, завершение, отмена любого заказа | MANAGER, SYSTEM_ADMIN |
| Создание сотрудников | SYSTEM_ADMIN |

## Стек

- Kotlin 2.2, Spring Boot 3.3 (Web, Data JPA, Security, Validation)
- PostgreSQL 16
- **Liquibase** — версионированные миграции схемы БД, применяются автоматически при старте
- **jjwt** — выпуск и проверка JWT-токенов
- **springdoc-openapi** — автогенерация документации API и Swagger UI
- **Testcontainers** — интеграционные тесты на настоящем PostgreSQL в Docker
- Docker Compose

## Архитектура

```
com.example.darkstore
├── presentation   — REST-контроллеры, DTO запросов/ответов, мапперы DTO ↔ модели
├── application    — бизнес-логика (сервисы), доменные исключения
├── dataAccess     — модели, репозитории, спецификации поиска
└── security       — JWT, фильтр аутентификации, правила доступа
```

Контроллеры только принимают запрос, валидируют DTO и вызывают сервис. Бизнес-правила
(переходы статусов, резервирование, проверка оплаты) находятся в сервисах и не зависят
от HTTP, поэтому поверх них можно добавить другой транспорт (gRPC, GraphQL) без изменения логики.
Ошибки преобразуются в единый JSON-формат в `GlobalExceptionHandler`.

## Запуск

Нужен установленный Docker.

### Вариант 1. Всё в Docker (рекомендуется)

```bash
cp .env.example .env
docker compose up --build
```

Поднимутся PostgreSQL и приложение. Миграции и демо-данные применятся автоматически.
Первая сборка образа занимает несколько минут.

### Вариант 2. Приложение из IDE или Gradle, БД в Docker

```bash
cp .env.example .env
docker compose up -d postgres
./gradlew bootRun
```

Файл `.env` должен лежать в корне проекта. Его читают и Docker Compose, и приложение.

### Что открыть

| Адрес | Что там |
|---|---|
| http://localhost:8080 | веб-интерфейс |
| http://localhost:8080/swagger-ui.html | документация API и тестовые запросы |
| http://localhost:8080/api/v1/products | каталог (JSON) |

### Демо-доступ

Администратор создаётся миграцией (только для разработки):

- телефон: `+70000000001`
- пароль: `admin123`

Через него можно создать сотрудников других ролей: `POST /api/v1/users/staff`.
В каталоге 25 демо-товаров, по 100 единиц каждого на складе.

## Переменные окружения

Все параметры задаются в файле `.env` в корне проекта (рядом с `docker-compose.yml`).
Готовый файл с рабочими значениями для локального запуска — `.env.example`:

```bash
cp .env.example .env
```

| Переменная | Назначение | Значение для локального запуска | Обязательна |
|---|---|---|---|
| `DB_NAME` | имя базы | `darkstore` | да |
| `DB_USERNAME` | пользователь БД | `postgres` | да |
| `DB_PASSWORD` | пароль БД | `postgres` | да |
| `DB_URL` | JDBC URL для запуска вне Docker | `jdbc:postgresql://localhost:5433/darkstore` | да, для варианта 2 |
| `JWT_SECRET` | ключ подписи JWT в base64, не меньше 32 байт | см. `.env.example` | да |
| `JWT_ACCESS_TTL` | время жизни access-токена | `15m` | нет |
| `JWT_REFRESH_TTL` | время жизни refresh-токена | `30d` | нет |
| `CORS_ALLOWED_ORIGINS` | разрешённые origin через запятую | `http://localhost:3000,http://localhost:8080` | нет |
| `SERVER_PORT` | порт приложения | `8080` | нет |
| `APP_LOG_LEVEL` | уровень логов приложения | `INFO` | нет |

Обязательные переменные не имеют значений по умолчанию: если `.env` не найден,
приложение не запустится с ошибкой `Could not resolve placeholder`.

Значения в `.env.example` учебные. Для реального окружения замени `DB_PASSWORD`
и `JWT_SECRET` (новый ключ: `openssl rand -base64 64`).

## Тесты

```bash
./gradlew test
```

Нужен запущенный Docker: интеграционные тесты сами поднимают временный PostgreSQL
и не трогают рабочую базу. Отчёт: `build/reports/tests/test/index.html`.

Покрыто:
- оформление заказа: расчёт суммы, резервирование, правила оплаты наличными, атомарность при нехватке остатка
- жизненный цикл статусов, недопустимые переходы (409), проверка ролей (403)
- отмена заказа владельцем и запрет отмены чужого заказа
- изменение состава заказа с пересчётом резерва и суммы
- конкурентное резервирование последней единицы товара
- регистрация, вход, ротация и отзыв refresh-токенов, доступ без токена
- поиск товаров по фильтрам, права на управление каталогом, валидация входных данных
- нормализация номера телефона

## Ограничения текущей версии

- Курьеры не назначаются на заказы: курьер видит заказы по статусу
- Поле `intercom` в адресе принимается, но пока не сохраняется
- Правила возврата денег и товара при отмене собранного заказа будут определены позже
- Демо-администратор и демо-данные предназначены только для разработки

## Планируемые интеграции

Внешние сервисы будут подключаться через интерфейсы в слое бизнес-логики
(`PaymentGateway`, `NotificationSender`, `AccountingSync`), а конкретные реализации
лягут в отдельные адаптеры. Так бизнес-логика заказов и склада не будет зависеть
от конкретного провайдера, и его можно будет заменить без переписывания сервисов.

### Онлайн-оплата — ЮKassa (ЮMoney)

Сейчас оплату подтверждает менеджер вручную (перевод заказа в `PAID`).
С интеграцией:
- при оформлении заказа с `paymentType = ONLINE` сервер создаёт платёж в ЮKassa
  и возвращает клиенту ссылку на страницу оплаты;
- ЮKassa присылает webhook об успешной оплате, сервер проверяет его подлинность
  и сам переводит заказ в `PAID`;
- при отмене оплаченного заказа автоматически создаётся возврат средств
  (здесь же будут закреплены правила возврата для собранных заказов);
- через ЮKassa формируются фискальные чеки по 54-ФЗ, без отдельной онлайн-кассы.

Обработка webhook-ов будет идемпотентной: повторное уведомление об одном
платеже не меняет состояние заказа второй раз.

### Push-уведомления — Firebase Cloud Messaging

Уведомления о событиях заказа на телефон клиента и сотрудников:
- клиенту — заказ принят, собран, передан курьеру, доставлен, отменён;
- складу — появился новый заказ на сборку;
- курьерам — заказ собран и готов к доставке.

Для этого появится хранение FCM-токенов устройств пользователя. Отправка
будет вызываться по событию смены статуса и выполняться асинхронно,
чтобы сбой доставки уведомления не влиял на сам заказ.

### Учётная система — 1С

Синхронизация с 1С для бухгалтерии и складского учёта:
- **из 1С в сервис** — номенклатура, цены, приход товара на склад
  (заменит ручной `POST /admin/stock/{productId}/add`);
- **из сервиса в 1С** — выполненные заказы как продажи, отмены и возвраты,
  фактические списания со склада.

Обмен планируется по HTTP (OData или HTTP-сервисы 1С) по расписанию
и по событиям. Каждая операция будет иметь внешний идентификатор,
чтобы повторная выгрузка не создавала дублей. При расхождении остатков
источником истины для прихода считается 1С, для резервов — этот сервис.
